# Project IRR Analyzer — Specification

Living specification. This file is the authority of record for what the application is and does. The changelog at the end grades every change. Current version: **v0.3.1** (2026-10-07).

## 1. Purpose and user

A purpose-built investment-appraisal application replacing spreadsheet work (the Invest for Excel class of tooling) for one practitioner: modelling project cost from burn-rate assumptions, solving the repayment stream required to hit a target IRR over a set term, and presenting the result in board-ready form.

## 2. Decisions of record (2026-10-07)

- Primary user: the owner alone. Personal tool; no multi-user, sharing, or permissions machinery.
- Deployment: desktop / local. The application runs on the user's machine; no hosting requirement. GitHub Pages deployment is out of scope. Tauri wrapper recommended at v1.0.
- Version 1.0 scope: as complete as possible — the full appraisal suite plus the financing layer.
- Projects: one at a time. Single-document model (one project = one file), like a spreadsheet workbook. No project database, no side-by-side comparison in v1.
- Currency handling: user-selected currency per project; no exchange-rate machinery in v1.
- Quality bar: correctness over the full input space, not only the built-in example. Invariant tests, an explicit numerical policy, and a no-silent-filtering validation contract are part of the definition of correct.

## 3. Product definition

Jobs to be done, in order:

1. Define the project cost plan (burn rate lines, escalations, one-time CAPEX, residual value).
2. Define the repayment structure (term, frequency, grace, escalation, balloon).
3. Set the target IRR and read the solved payment stream, with verified achieved IRR.
4. Stress the result (scenarios, sensitivity tables, WACC benchmark).
5. Model the financing (debt/equity split, drawdown, interest, DSCR).
6. Present it (generated slide deck; exports to PDF and XLSX).

## 4. Calculation engine specification

### 4.1 Time basis

All computation on a monthly-resolution cash-flow vector; annual aggregation for reporting. Monthly rate from annual rate: r_m = (1 + r)^(1/12) - 1. Every metric derives from this one vector; no metric is computed independently of it.

### 4.2 Cost model

- Cost lines, any number: recurring (annual amount, start year, duration, escalation %/yr) or one-time (amount at a given year).
- Optional per-year override table on any recurring line (Invest-for-Excel-style flexibility).
- Residual value: first-class input, a positive terminal cash flow at a set year. Placement of record (v0.3): the collections side — it participates in NPV(collections) and in the solver and is never netted against costs; zero residual is byte-identical to absent.
- Categories for grouping (personnel, infrastructure, CAPEX, other).
- Operating cost lines (v0.3.1 scope of record, user request 2026-10-07): rent, lease, concession, OPEX, and maintenance lines that run alongside collections during the repayment period. A maintenance rule derives a yearly cost from CAPEX (rule of thumb: 0.5 percent of total CAPEX per year, payable from the first year collections begin; changeable to a fixed sum or another percentage). Operation-period costs are costs of the single vector: they raise the solved payment and lower the achieved IRR. Convention of record: operation-period cost lines never move the repayment start — the repayment start is either set explicitly by the user or derived by default from the project-fulfillment lines alone, so these costs run alongside collections rather than deferring them. Delivered at v0.3.1: operating lines (category operating, recurring-line shape) spread monthly like burn lines, excluded from the last-cost-year derivation and the horizon, clipped to the collection window [firstCollectionMonth, lastInflowMonth] (lastInflowMonth = max(lastPaymentMonth, residual month)); the engine emits each line nominal span, effective window, and total, and the UI displays them — clipping is never silent, and a line falling entirely outside the window is a surfaced input error naming the line and the window. The maintenance rule is mode off / percent / fixed, the basis of record resolved to total CAPEX (percent per year of the sum of one-time line totals) or a fixed annual sum, running monthly from the first collection month with no escalation; the derived line is labeled with its basis and traceable in the cost composition.

### 4.3 Repayment solver — three modes

- Mode A (primary): given target IRR and term, solve the periodic payment P so that NPV(collections) = NPV(costs) at the target rate, honouring frequency, grace, escalation, and balloon.
- Mode B: given P and target IRR, solve the required term (rounded up to whole payment periods).
- Mode C: given P and term, report the achieved IRR (no solving).
- The achieved IRR is always verified numerically (bisection on the NPV function) against the solved structure.
- Delivered at v0.3: Mode B (solveTerm) returns the minimum whole payment count with fractional term years allowed, lastPaymentMonth = start + (n - 1) x spacing, and surfaces infeasibility as null with the discounted shortfall; Mode C evaluates a given payment through the computeModel fixedPayment option; the engine emits goalMet with meets-or-exceeds semantics, superseding the v0.2 UI-side goal check.
- Collection indexation (v0.3.1 scope of record, user request 2026-10-07): CPI-style indexation of collections — collections in year k are scaled by (1 + rate)^(k-1), rule of thumb 2 percent per year when enabled. The arithmetic already exists (the payment escalation parameter). Delivered at v0.3.1: surfaced and labeled Indexation (CPI) percent per year with the 2 percent rule-of-thumb hint; single rate only — per-year overrides deferred by decision of record (2026-10-07); the engine arithmetic is unchanged.
- Repayment start override (v0.3.1 scope of record, user request 2026-10-07): the first collection year is user-settable, including during the cost period — large projects may begin renting out parts of a property before construction completes. Default: derived as the last project-fulfillment cost year plus grace, exactly as today. When collections overlap the cost period, the net vector can change sign more than once; the ambiguity policy of section 4.7 applies, the ambiguity flag is expected rather than exceptional in such structures, and the solver identity still holds at the target rate. Delivered at v0.3.1 with the decision of record (2026-10-07): the explicit start replaces the derivation — the first payment month is firstCollectionYear x 12 for all three modes — and grace must be zero when the override is set (a surfaced input error otherwise); the maintenance window recomputes to the actual collection start.
- Tariff-based collections (v0.3.2 scope of record, user request 2026-10-07): the collection side may be expressed as a tariff decomposition rather than a bare amount. The user defines type rows — each a free-text descriptor (informational only), a weight (a charging coefficient, not a physical mass), and a lift count per year — in a user-determined rows-by-years grid that represents how the costs would actually be recovered (example of record: container lifts over a quay — dry and reefer, loaded, empty, and transhipment — at weights such as 1/2, 0.5/1, and 2/4 for 20- and 40-foot boxes). The weighted volume of a year is the sum over rows of weight times lifts. Two-step flow of record: step one derives the required collection schedule from the target IRR, CAPEX, term, and all other factors (the existing Mode-A solve); step two answers how that requirement is actually recovered, down to currency per lift. Price modes of record, all supported because flexibility is an explicit requirement: (a) solved per year, the default — the unit price of a year is the required collections of that year divided by its weighted volume, and the per-lift charge of a row is its weight times that unit price, so flat volumes inherit the schedule escalation automatically; (b) a stable indexed tariff — one base unit price in first-year terms with an escalation rate, solved so that NPV(tariff collections) = NPV(costs) at the target IRR, a genuine solve variant whose revenue profile is volume-shaped rather than annuity-shaped (a constant nominal tariff is the zero-escalation case); (c) manual per-year prices — user-set, the engine evaluating the resulting profile without solving. The required schedule may alternatively be a user-entered fixed amount per year in place of the solved schedule, the achieved IRR then being reported as the outcome. Conventions of record: mode (a) never changes the solved schedule; mode (b) differs from the annuity by design and its achieved IRR equals the target by construction; residual value remains a separate first-class input and is never decomposed into per-lift prices; a year with zero weighted volume against a positive required collection is a surfaced infeasibility, never a silent zero. The feature composes with the v0.3.1 conventions (the repayment start override and indexation).

### 4.4 Metrics

- NPV at target IRR and NPV at WACC (benchmark discount rate input).
- IRR: bracketed bisection on the NPV function. The bracket is found by a finite grid scan for a sign change over monthly rates [-0.9, 6.0] (96 steps), then bisection to an NPV below 1e-9 or 300 iterations; the monthly root is annualized as (1 + r_m)^12 - 1. An all-zero flow vector yields no IRR. (DEFECT-001 repair of 2026-10-07: the original unbounded bracket [-0.9999, 10] evaluated the NPV at a degenerate rate where denominators underflow, and could collapse to the meaningless value 11^12 - 1.)
- MIRR with explicit finance rate and reinvestment rate.
- Payback (nominal) and discounted payback (at WACC), interpolated, both in years.
- Profitability index: NPV(collections at WACC) / NPV(costs at WACC).
- Total cost, total collected, nominal gain, collection-to-cost ratio.
- Conventions of record, delivered at v0.3: MIRR = (FV of positive net flows at the reinvestment rate to month N / |PV of negative net flows at the finance rate to month 0|)^(12/N) - 1 on the monthly vector, null when either side is empty; profitabilityIndex = npvCollectionsAtWacc / npvCostsAtWacc, null when the cost side is non-positive; discounted payback applies the nominal interpolation rule to the discounted cumulative and equals the nominal payback at WACC 0; goalMet = achievedIrr !== null && achievedIrr >= target/100 - 1e-9.

### 4.5 Financing layer (v1.0 scope)

- Debt share per cost line; drawdown follows the cost schedule.
- Interest during construction capitalized into the debt balance at the debt rate.
- Debt repayment: annuity or equal-principal, with its own term and optional grace.
- Equity cash flow = project cash flow + debt drawdown - debt service; equity IRR reported beside project IRR.
- DSCR per year: collections / (interest + scheduled principal); minimum-DSCR reported.

### 4.6 Scenarios and sensitivity

- Three named assumption sets (base / optimistic / pessimistic): global multipliers on burn rate, escalation shift, IRR-goal shift, term shift.
- One-way sensitivity (tornado) on the required payment: burn rate, target IRR, term, escalation.
- Two-way tables: payment vs. term; payment vs. target IRR; payment vs. balloon.

### 4.7 Numerical and validation policy (of record, 2026-10-07)

- Precision: all computation in IEEE-754 double precision with no intermediate rounding. Rounding occurs only at the display and export boundary.
- Display: values are rounded to the currency's minor unit for presentation; a displayed total is computed from unrounded values, so displayed component rows may differ from a displayed total by at most one minor unit.
- Validation: input errors surface; no silent filtering. A cost line with an empty name, a non-positive amount, or a start year below one is an error to be reported, not a line to be quietly dropped. (Deviation of record: the prototype silently dropped invalid lines; the tool of record reports them. Enforced since the v0.1.1 hardening pass.)
- IRR non-uniqueness: for net-flow vectors with more than one sign change, the IRR may not be unique. The engine counts sign changes across non-zero flows and reports an ambiguity flag alongside the achieved IRR; the UI must warn when the flag is set. The solver returns the first bracket found from the left of the scan grid; this limitation is documented, not hidden. Robustness of record (v0.3.1, script-verified): in every pinned overlapping-collection case the first bracket contains the target monthly rate and the net NPV is strictly positive at every scanned rate below it, so the achieved IRR equals the target and the goal check holds even where the ambiguity flag is set; the disclosure still renders.
- Solver bounds: the IRR search never evaluates the NPV outside monthly rates [-0.9, 6.0].
- Determinism: identical inputs produce identical outputs; the engine contains no randomness, clock, or I/O.
- Directional claims of record (script-verified 2026-10-07): a longer grace strictly raises the solved payment at positive target rates (deferral discounts every collection; at a zero target rate the payment is invariant to grace); a larger balloon strictly lowers the payment; a higher target IRR strictly lowers the cost NPV; a longer term strictly lowers the payment.
- Ambiguity reachability, limitation of record (v0.2.0): under the current input model the ambiguity flag is unreachable — collections begin at or after the last cost month, so the net vector crosses zero at most once. Superseded at v0.3: with residual value constructible, net vectors with multiple sign changes exist (residual 2,000,000 at year 1 yields three sign changes), and the warning is now tested against a real engine result; the component-contract tests remain for the display logic in isolation.

- Standing rule: every pass keeps the golden fixture green. A change to any golden value is a change to model behavior and requires an explicit, spec-graded decision before implementation — never a silent pin update.

## 5. Application architecture

- Layering: (1) pure calculation engine, no I/O, deterministic; (2) UI layer; (3) storage layer; (4) presentation/export layer. The engine is identical in tests, UI, and exports.
- Technology: TypeScript engine; React web UI (Vite); at v1.0 packaged as a desktop application via a Tauri wrapper.
- Storage: local project files (JSON, schema-versioned) — open, save, and recent-files. One project per file. No cloud, no accounts.
- Presentation mode: the five-slide deck generated from the live model (title, investment, repayment, returns, summary), navigable by keyboard; print-to-PDF from the same rendering; XLSX schedule export.
- Project settings and calendar-year labeling (v0.3.1 scope of record, user request 2026-10-07): a project-level start-year setting drives calendar-year headers (for example 2026, 2027, 2028) on every per-year column presentation — cost-line per-year overrides, the repayment yearly schedule, operation-period lines, tariff volume grids, results, and the presentation deck — so all sections share one easily discernible left-to-right flow of time. The settings surface is the natural home for this and future project-level details. Convention of record: the labels are a presentation-layer concern only; the mapping year k to startYear + k - 1 lives exclusively in the UI and export layers, the engine never receives the start year, and no metric, pin, or golden value can depend on it. Validation: integer start year (recommended range 1900 to 2200); the field is optional and saved in the project file schema. Delivered at v0.3.1 in part: the shared header helper exists and serves the results table (both behaviors pinned); the remaining per-year surfaces (the presentation deck and the other per-year tables) and the 1900–2200 enforcement are carried to the next web pass, and settings persistence waits for project-file save/load (v1.0).
