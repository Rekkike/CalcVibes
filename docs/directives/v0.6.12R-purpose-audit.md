## The purpose of record

The app's stated purpose lives in three places: docs/SPECIFICATION.md (the graded specification — the charter and the delivered-behavior sections), the controller's rulings of record relayed through this directive (the presentation-honesty bar: zero-based comparisons, live-model figures only, the reading-form discipline, the never-retyped discipline, cross-surface terminology consistency, declared-data-beats-inference), and the user's stated intent (an investment-appraisal calculator: project cost burn, repayment solving against a target IRR, multi-contract capability, financing, scenarios, and a presentation deck fit for the uninitiated reader). The audit measures the tree against all three.

## The five audit lenses

1. PURPOSE CONFORMANCE — every user-facing surface vs the charter it serves: does the surface do what the app promises, visibly and honestly? A surface that works as coded but fails the promise it signals to the user is a finding.
2. SPEC-VS-TREE — each spec section's stated behavior vs the implementation reality: stated-but-unimplemented, implemented-but-unstated, implemented-differently.
3. INTERNAL CONSISTENCY — vocabulary and format consistency across surfaces (the reading-form discipline, the calendar-label vocabulary, the token vocabulary, the deck vocabulary), plus dead code, unused exports, stale comments, and hardcoded literals that the vocabulary of record has superseded.
4. PIN COVERAGE — the Task A lesson generalized: which user-visible behaviors would survive a mutation undetected today? List the unpinned behaviors that matter, with the surface each one guards.
5. EDGE OBSERVATION — input shapes that error, warn, or render oddly: observed and reported, not fixed. The golden battery and the standing fixtures are the reference shapes; the audit probes around them read-only (no working-copy probes that touch tracked files without a clean restore, and no probes at all if the safety check withholds a verdict).

## The findings format

Every finding carries: an ID (AUD-1, AUD-2, ...), a category (A defect / B spec-gap / C purpose-gap / D improvement / E stale-or-dead), evidence (file:line and the observed behavior), a severity (blocking / material / cosmetic), and the spec section referenced — or "no spec coverage" where the spec is silent. A one-line suggestion may be appended per finding, clearly marked non-binding: the builder reports; the controller and the user adjudicate, prioritize, and compose the remediation. No recommendation is executed in this pass.
