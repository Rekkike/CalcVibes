## 2. Decisions of record (settled with the product owner, 2026-10-07)

1. Maintenance basis: total CAPEX — the sum of the one-time (capex) line totals of the project — charged as a percent per year or a fixed annual sum.
2. Indexation: a single rate per project. The existing repayment.paymentEscalation arithmetic is the engine of record; per-year indexation overrides are deferred.
3. An explicit repayment start replaces the derivation. When the override is set, grace must be zero; any nonzero grace is a validation error.
4. When the project start year is unset, per-year columns show generic Year-k labels.

## 3. Conventions of record (new in this pass)

3.1 Operating lines. A new cost category "operating" (rent, lease, concession, OPEX, and similar lines that run alongside collections). An operating line has the shape of a recurring cost line: id, label, amount per year, startYear, yearCount, escalation. It is spread monthly exactly like a recurring burn line: month amount = amount × (1 + escalation/100)^(year − startYear) / 12.

3.2 Operating lines never move the repayment start and never extend the horizon. They are excluded from the last-cost-year derivation and from the horizon computation. They enter totalCost and costNpv; through the single-vector principle they raise the solved payment and lower the achieved metrics automatically. No special-case arithmetic.

3.3 Clipping. Operating months are restricted to the collection window [firstCollectionMonth, lastInflowMonth], where lastInflowMonth = max(lastPaymentMonth, residual month) when a residual value is configured. Rationale of record: these lines represent operation-period costs; there is no operation outside the window, and unclipped tails after the last inflow corrupt the IRR bracketing (script-verified: with clipping the first bracket stays on the target root). Clipping is never silent: the engine emits each operating line's nominal span, effective window, and total, and the UI displays them. An operating line falling entirely outside the collection window is a surfaced EngineInputError naming the line and the window — no silent zero contribution, per the no-silent-filtering contract.

3.4 Maintenance derived line. Configuration: mode off | percent | fixed. Percent mode: annual amount = percentPerYear/100 × total CAPEX (decision 2.1). Fixed mode: the given annual amount. The line runs monthly (annual amount / 12) from the first collection month through the horizon, clipped at lastInflowMonth like any operating line; it carries no escalation in this pass. It appears as a derived, labeled, traceable line in the cost composition, labeled with its basis (for example: Maintenance, derived: 0.5% of total CAPEX). Percent mode with zero total CAPEX yields a zero-amount line: legal and explicit, not a clipping case.

3.5 Repayment start override. Optional field repayment.firstCollectionYear. When set (integer ≥ 1), the first payment month is firstCollectionYear × 12; this replaces the derived lastCostYear + grace start for all three modes (A, B, and C consume the same start month). Grace must be zero when the override is set; otherwise a surfaced EngineInputError states that the override replaces the derivation and grace must be zero. With collections overlapping the cost period, more than one sign change and irrAmbiguous true are expected, not exceptional; the section 4.7 first-bracket policy governs and the solver identity still holds at the target rate.

3.6 Indexation. The existing paymentEscalation field and arithmetic are unchanged in the engine. This pass surfaces and labels it in the web UI as "Indexation (CPI) % per year" with the rule-of-thumb hint 2%. No new math.

3.7 Calendar-year labeling. Presentation layer only. The project file gains settings { startYear: null }. When set (integer, validated at the file/UI layer to 1900–2200), every per-year column header renders startYear + k − 1 (for example 2026, 2027); when unset, generic Year-k labels (decision 2.4). Exactly one shared header derivation serves every per-year table: cost-line yearly grids, repayment yearly schedule, operating lines, results, and the presentation deck. The mapping lives exclusively in the UI layer; fromFile strips settings alongside schemaVersion; the engine never receives the start year, and no metric, pin, or golden value may depend on it.

3.8 IRR robustness under ambiguity (script-verified for every pinned case of this pass). For every case below with more than one sign change, the 96-step grid scan over [−0.9, 6.0] finds its first sign change in the monthly bracket [−0.0375, 0.034375], which contains the target monthly rate, and the net NPV is strictly positive at every scanned rate below the target (5,000-point scan; minimum on the order of +5.0 × 10^4). achievedIrr therefore equals the target and goalMet is true in all pinned cases, even where irrAmbiguous is true. The ambiguity disclosure must still render; ambiguity is disclosed, never hidden.
